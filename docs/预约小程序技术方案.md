# 四个小姐姐的店预约小程序技术方案

> 实施状态：首版代码骨架已完成，业务数据已切换为 CloudBase 原生 MySQL 适配层，MySQL 线上连接、演示数据初始化、云函数 SQL 读链路和静态后台产物已验证。管理员登录会话、真机支付、真实退款、回调通知验签和恢复演练仍需按本文清单验证后才能上线。

## 1. 目标与首版边界

这是一个单店美业预约系统，包含顾客微信小程序、店员/技师工作台和电脑/平板管理后台。服务大项为美甲、美眉、纹绣；每个大项包含小项目，小项目下有多个款式；一单只有一个小项目、一个款式、一位技师和一位顾客。

首版规则如下：

| 规则 | 实现口径 |
| --- | --- |
| 预约窗口 | 未来 14 天；开始时间至少提前 60 分钟；候选时间按 15 分钟步长生成 |
| 技师容量 | `technician_days` 每日占用文档作为争抢锁；同一技师同一时间只允许一个有效占用 |
| 支付 | 全额预付；创建订单后占位 5 分钟；支付结果只认回调或服务端查单 |
| 到店 | 店员或对应技师将 `RESERVED` 转为 `ARRIVED`，再转 `IN_SERVICE` |
| 未到店 | 开始时间后默认 30 分钟仍未核销，自动取消并发起整单退款 |
| 自主取消 | 到店核销前允许取消；已支付订单进入退款流程，未支付订单释放占用 |
| 积分 | 实付每满 1 元得 1 分；20 分抵 1 元；单笔最多抵项目金额 10% |
| 统计 | 只统计小程序订单；收款、退款、完成服务分别记录，不混用现金流和服务收入 |

不包含组合项目、定金尾款、储值卡、线下消费补录、直接改期和多店管理。改期由取消退款后重新预约替代。

## 4. SQL 索引和确定性 ID

执行 [`mysql-schema.sql`](mysql-schema.sql) 创建表和基础索引；当前业务高频筛选由服务端适配层完成，后续可按真实数据量为 JSON 字段增加生成列索引：

| SQL 表 | 主键 / 查找键 |
| --- | --- |
| `orders` | `id`；业务字段在 `data` 中按用户、状态和日期筛选 |
| `technician_days` | `id = ${technicianId}_${date}` |
| `payments` | `id = pay_${orderId}`，同时保存 `merchantOrderNo` |
| `refunds` | `id = rf_${orderId}`，同时保存 `refundNo` |
| `points_ledger` | 由确定性流水 ID 防重，业务字段在 `data` 中筛选 |
| `points_accounts` | `id = openid` |
| `jobs` | 由任务 ID 防重，业务字段在 `data` 中按状态和时间筛选 |
| `works` / `services` / `technicians` | 业务字段在 `data` 中按目录状态和排序筛选 |
| `settings_versions` | `id = v${version}`，按发布状态和版本筛选 |

预约事务只读取和写入同一技师、同一日期的 `technician_days` SQL 行，通过版本化占用数组判断左闭右开区间冲突。外部微信支付调用必须在事务提交后执行。

## 6. 订单、资金和积分状态机

预约主状态：

```text
PENDING_PAYMENT ──支付确认──> RESERVED ──确认到店──> ARRIVED ──开始服务──> IN_SERVICE ──完成──> COMPLETED
       │                         │                    │                    │
       └─查单/关单───────────────┴─用户取消/未到店──────┴─仅管理员业务处理──────┘
```

- `PENDING_PAYMENT` 超时必须先查单；确定未支付后关单、释放占用、解冻积分。
- 支付成功但订单已取消时，不恢复冲突时段，直接创建或继续同一退款单。
- `RESERVED` 取消后写 `refundStatus=PROCESSING/PENDING_CONFIG`，退款到账前不显示“已到账”。
- `CANCELLED_NO_SHOW` 由任务在 `startAt + noShowGraceMinutes` 后触发，自动发起整单退款。
- 重复回调、重复查单、重复任务和双设备操作均使用确定性 ID/幂等流水，不能重复记账。

积分动作：

1. 创建订单时按服务端报价计算 `pointsToUse`，`available -= pointsToUse`、`frozen += pointsToUse`。
2. 支付确认时 `frozen -= pointsToUse`，写一次 `CONSUME` 流水。
3. 未支付关闭或取消时 `frozen -= pointsToUse`、`available += pointsToUse`，写一次 `UNFREEZE` 流水。
4. 服务完成按 `floor(paidFen / pointRateFen)` 发放，写一次 `EARN` 流水。
5. 整单退款成功后退还已消耗积分，写一次 `REFUND` 流水；同时冲回已发放的 `EARN` 积分，必要时写入 `points_accounts.debt`，后续奖励先抵扣欠额，不直接篡改历史流水。

## 7. 微信支付 API v3 预留

代码已包含：普通商户直连 JSAPI 下单、RSA-SHA256 请求签名、调起支付参数签名、主动查单、关单、退款申请、平台通知验签和 AES-256-GCM 解密。`payment-callback` 作为独立入口保留原始请求体，并区分支付成功与退款成功事件。

当前不需要填写资质即可开发页面和业务流程。缺少任何服务端参数时：

- `preparePayment` 返回配置缺失，订单仍保持待付款并可查看；
- 前端不能根据 `wx.requestPayment` 回调直接把订单改为已预约；
- 取消和超时退款进入 `PENDING_CONFIG` 或补偿任务，不伪造退款到账；
- 管理后台只显示缺失变量名称，不显示密钥值。

待补变量见 [`微信支付接入清单.md`](微信支付接入清单.md)。真实上线还必须在真机完成：支付成功回调、支付取消、支付超时迟到支付、重复回调、用户取消退款、未到店自动退款和退款到账回调。

## 8. 页面规格和交互

顾客端底部导航为：首页、项目、预约、我的。

- 首页：门店信息、三类服务、精选项目、作品横向浏览、营业须知。
- 项目：先选大项，再选小项目；点击小项目进入独立款式页，空数据、图片失败有兜底。
- 项目/款式详情：大图、价格、时长、技师和预约入口。
- 预约：技师→日期→时间→积分→手机号→金额确认；持续展示项目金额、抵扣、实付和支付依据。
- 订单：待付款、待到店、已到店、服务中、已完成、退款状态；区分申请、处理中、到账、异常。
- 工作台：按角色展示自己的订单；确认到店、开始服务、完成服务有服务端状态校验。
- 个人中心：用户资料、积分、订单、客服、隐私和工作台入口。

视觉使用奶油白背景、低饱和玫瑰色主按钮、深灰正文、真实作品大图；点击区域至少 44 逻辑像素，使用弹性布局和安全区，不依赖固定屏幕高度。

## 9. 管理后台

`admin/` 是 Vue 3 + TypeScript + Vite 应用，适配电脑和平板。没有设置 `VITE_ADMIN_API_URL` 时只显示演示数据；有配置时通过 HTTPS 管理 API 调用 CloudBase 业务函数，使用部署环境的登录会话，不把商户密钥放进前端。

权限：

- 店主：项目、作品、技师、排班、规则、退款、积分调整、统计和导出。
- 店员：订单、核销和服务操作；只看必要联系方式。
- 技师：自己的日程和预约，不能访问其他技师订单。

后台不能直接编辑订单实付金额、支付状态或积分余额；所有改变都必须通过业务动作、确定性流水和审计日志完成。

## 10. 任务、预算、安全和恢复

- `jobs` 函数使用租约、到期重领、指数退避和失败计数；重点任务是支付关单、未到店、退款补偿和支付/退款对账。
- 使用 CloudBase Serverless MySQL，采用按需计费和自动暂停；不启用 Redis、预置并发或自动升级，目录分页、图片压缩、无实时监听，统计可延迟。
- MySQL 不向客户端开放直连；云函数每次执行身份、对象归属、角色、状态和金额校验。
- 生产环境必须把 `CONTACT_ENCRYPTION_KEY`、微信支付参数和平台证书放进 CloudBase 服务端受控配置；不提交 `.env`、私钥、Token 或完整回调报文。
- 每日加密备份保留 7 个日备份和 4 个周备份；每月恢复演练，目标数据损失窗口不超过 24 小时、人工恢复目标 4 小时。若固定预算无法容纳备份，标记为上线阻碍。

## 11. 部署顺序

1. 在微信开发者工具打开项目，确认 `cloud-config.js` 的环境 ID和当前环境一致。
2. 运行 `npm run db:schema` 应用 `docs/mysql-schema.sql`，确认 MySQL 表和基础索引。
3. 配置各云函数的 MySQL 内网连接环境变量和 VPC，再部署 `seed`；仅在确认参数为 `SEED_DEMO_DATA` 时初始化演示目录。
4. 执行 `npm run prepare:functions`，把共享 SQL 适配层准备到 `jobs`、`payment-callback`、`admin-api` 和 `seed` 函数目录，再分别云端安装依赖部署 `api`、`jobs`、`payment-callback`、`admin-api`。
5. 配置定时触发器和 `payment-callback` 公网 HTTPS 入口；入口必须能验证原始请求体签名。
6. 配置管理 API HTTPS 地址，运行 `cd admin && npm install && npm run build`，将 `admin/dist` 部署到静态托管。
7. 仅在资质审核完成后填写支付环境变量，先用沙箱/可控测试订单验证，再做真实支付和退款闭环。
